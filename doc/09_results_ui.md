# UI результатов анализа

## Структура страницы

Страница `/analysis/<run_id>/` построена как master-detail:

1. **Левая колонка (список событий)** — показывает превью каждого абзаца и позволяет выбрать событие.
2. **Правая колонка (детали выбранного события)** включает:
   - **Текст события** с подсветкой извлеченных атрибутов.
   - **Таблицу основных атрибутов**: дата/время, подразделение, нарушители.
   - **Блок “Тип события”**: определено (по классификатору) vs в БД.
   - **Блок “Комментарии”**: пояснения о несовпадениях.

При выключенном JS выбор события работает через `?event=N`.

## Логика метрик и статусов

В `match_event()` рассчитываются и возвращаются дополнительные поля:

- `time_delta_minutes` — дельта между извлеченным временем и временем в БД.
- `offenders_score_percent` — доля совпавших нарушителей (0–100).
- `offenders_counts`:
  - `svodka_total` — количество нарушителей в сводке,
  - `portal_total` — количество нарушителей в БД,
  - `matched` — совпавшие нарушители по строгим правилам,
  - `dob_mismatch` — ФИО совпало, но полные даты рождения разные,
  - `missing_in_portal` — есть в сводке, но нет в БД,
  - `missing_in_svodka` — есть в БД, но нет в сводке.
- `subdivision_match_percent` — похожесть названия подразделения (SequenceMatcher).
- `portal` — срез БД (дата, подразделение, нарушители, тип события, статья).
- `predicted` — результат классификации (тип и статья).

## Правила подбора события

1. **Приоритет subdivision + time**: если известны подразделение и время, сначала ищется
   событие в `portal_db` с тем же подразделением и временем в окне ±30 минут. При наличии
   нескольких кандидатов берется ближайший по времени.
2. **Fallback по нарушителям**: если кандидатов по подразделению и времени нет,
   применяется прежнее правило “2 из 3” (время + нарушители или подразделение + нарушители).
3. **Сравнение нарушителей** выполняется после выбора события и не блокирует матч, если
   уже найдено совпадение по подразделению и времени.

## Сравнение дат рождения

Дата рождения считается совпавшей при правилах:

- Полные даты равны.
- Допускается “годовая” дата в виде `01.01.YYYY`, если другая сторона содержит полную дату
  того же года.
- Если одна из дат пустая или содержит заглушку `1900-01-01`, дата рождения игнорируется
  при сравнении.

## Отображение времени

Внутри системы даты могут храниться в timezone-aware виде (с часовым поясом), потому что
математика с интервалами и сравнениями должна быть корректной. На UI все временные
значения приводятся к локальному времени проекта и отображаются без часового пояса в
формате `DD-MM-YYYY HH:MM` (24h), а даты без времени — `DD-MM-YYYY`, чтобы оператор видел единый локальный формат без смещения.

### Значки статуса

| Атрибут | Зеленый (✓) | Желтый (!) | Красный (✕) |
| --- | --- | --- | --- |
| Дата/время | `matched` и `time_delta_minutes <= 30` | `matched` и `time_delta_minutes > 30` | `not matched` или время отсутствует |
| Подразделение | `matched` и нет `diffs["subdivision"]` | `matched` и есть `diffs["subdivision"]` | `not matched` |
| Нарушители | `matched == portal_total` и нет `dob_mismatch/missing` | `0 < matched < portal_total` или есть `dob_mismatch/missing` | `matched == 0` и `portal_total > 0` (или есть `dob_mismatch/missing`) |

## Подсветка атрибутов в тексте

Подсветка выполняется сервером с помощью `highlight_text()`:

- Сначала текст экранируется, чтобы предотвратить XSS.
- Подсветка добавляется только для фрагментов, найденных в тексте:
  1. **Дата/время** — по первому совпадению extractor-ом для дат.
  2. **Подразделение** — поиск подстроки по названию (case-insensitive).
  3. **Нарушители** — поиск по полному имени (case-insensitive).
- Каждому типу атрибута назначается цвет (зеленый/желтый/красный) по правилам из таблицы выше.

Подсвеченные фрагменты добавляются в DOM как безопасные `<span class="hl ...">...</span>`.

## Роли интерфейса (User/Admin)

UI определяется только ролью пользователя, без переключателя и без хранения режима в сессии:

- **staff/superuser** — всегда admin/diagnostic layout;
- **non-staff** — всегда minimal user layout.

### Поведение на странице результатов

- **Non-staff**:
  - диагностические панели скрыты;
  - блок предпросмотра обрезки/якорей остаётся в `<details>` и по умолчанию свернут.
- **Staff/superuser**:
  - диагностические секции раскрыты по умолчанию;
  - отображаются diagnostic/debug блоки;
  - доступен debug.zip (при выполнении условий ниже).

### Debug tools и `debug_mode`

Глобальный флаг `FeatureFlags.debug_mode` сохраняет прежнюю роль и обязателен для debug.zip:

- Если `debug_mode=OFF`:
  - в admin-режиме показывается предупреждение «Debug отключен администратором»;
  - ссылка debug.zip скрыта/недоступна.
- Если `debug_mode=ON`:
  - в admin-режиме показываются debug-инструменты;
  - debug.zip доступен по правам.

### Права на debug.zip

Эндпоинт debug.zip разрешает доступ только при `debug_mode=ON` и одном из условий:

- владелец запуска (как раньше), либо
- staff-пользователь (даже если не владелец запуска).

Для non-staff и non-owner доступ запрещён (без утечки артефактов).
